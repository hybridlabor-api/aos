# Defensive Audit Checklists

Derived from the Claude-Red body of knowledge, inverted into verification questions.
Every item is something an auditor **checks for presence and correctness** in the
defended codebase. Work only the sections the change or system under audit touches.
Mark each item `pass`, `fail`, or `n/a`; an unmarked item is not a pass, and a
section you could not verify is reported as **could not check**.

Severity guidance when a check fails:

| Severity | Meaning |
|---|---|
| `blocking` | Exploitable by any untrusted party with the exposure the system already has. Fix before ship. |
| `high` | Exploitable with modest preconditions (a valid low-privilege account, a known config). Fix or ticket before ship. |
| `medium` | Requires special conditions or adds defense-in-depth gaps. Ticket. |
| `low` | Hygiene and hardening. Backlog. |

---

## 1. Authentication & Session Management

- [ ] Passwords are hashed with a dedicated password hash function (bcrypt, scrypt, or argon2 family) — never fast general-purpose hashes, never reversible encoding.
- [ ] Salt is unique per credential and generated by the hashing library itself.
- [ ] Password/secret comparison uses constant-time comparison functions, not `==`.
- [ ] Login, password reset, and MFA endpoints are rate-limited per account and per source, with exponential backoff or lockout.
- [ ] Authentication error messages do not reveal whether the account exists ("invalid credentials", not "unknown user").
- [ ] Session identifiers are regenerated on privilege change (login, password change, role elevation).
- [ ] Session cookies carry `Secure`, `HttpOnly`, and an appropriate `SameSite` attribute.
- [ ] Session lifetime and idle timeout are explicitly configured — no infinite sessions.
- [ ] Server-side session invalidation exists: logout actually destroys the session server-side, and "log out everywhere" is possible.
- [ ] Password reset tokens are single-use, short-lived, and invalidated on use or on new request.
- [ ] MFA, where present, is enforced server-side — client-side toggles cannot bypass it.
- [ ] JWTs (if used): algorithm is pinned server-side; signature, issuer, audience, and expiry are all verified; tokens are rejected after logout via a denylist or short lifetime.
- [ ] Service-to-service authentication uses scoped credentials (mTLS, signed tokens), not shared long-lived keys in config.

## 2. Authorization & Access Control (IDOR, BOLA)

- [ ] Every server-side handler performs its own authorization check — the client, frontend route guard, or API gateway is never the only gate.
- [ ] Object access resolves ownership from the **server-side session/identity**, never from a client-supplied user or account identifier alone.
- [ ] Sequential or guessable object identifiers (numeric IDs, slugs) are backed by an ownership/permission check, so direct object references cannot be swapped.
- [ ] Default authorization state is **deny**; new endpoints and new object types start inaccessible and are opened deliberately.
- [ ] Role/permission checks are centralized (one policy layer, middleware, or decorator) rather than re-implemented per handler.
- [ ] Privilege escalation paths checked: a lower-privileged role cannot invoke operations that only a higher role should reach, including via batch/bulk endpoints.
- [ ] Tenant isolation verified: every query that reads or writes multi-tenant data filters by tenant, including exports, search, and background jobs.
- [ ] Admin and internal-only endpoints are not reachable through alternate routes (old API versions, debug routers, secondary ports).
- [ ] File/record deletion and export operations re-check authorization at execution time, not only at link-rendering time.
- [ ] API responses return only fields the caller is entitled to — no over-fetching of other users' or internal fields.

## 3. Input Validation & Injection

### General

- [ ] All external input (query, body, headers, path segments, files, webhooks, message queues) is validated against an explicit schema at the trust boundary.
- [ ] Validation is allow-list shaped (type, length, range, format, enumeration) rather than deny-list filtering.
- [ ] Canonicalization happens before validation for anything that becomes a path, URL, or identifier.

### SQL injection

- [ ] Every query uses parameterized statements or a query builder/ORM binding — no string concatenation or f-string/format interpolation of user input into SQL, in **any** file, including "harmless" admin scripts.
- [ ] Dynamic ordering/filtering (sort column, filter name) maps through a fixed allow-list of column/field names, never through raw input.
- [ ] Stored procedures and raw-SQL escape hatches accept parameters, not concatenated fragments.
- [ ] Database accounts run with least privilege (no DDL, no cross-database access unless required).

### Command injection

- [ ] Shell invocation is avoided where a library/API call exists; when a subprocess is unavoidable, arguments are passed as an argument array — never through a single shell-parsed string.
- [ ] User input never reaches a shell interpreter, template engine `eval`, code `eval`, or dynamic deserialization of executable formats.
- [ ] Working directories and environment for spawned processes are pinned; inherited secrets are pruned from child-process environments.

### Server-Side Request Forgery (SSRF)

- [ ] Every outbound request built from user-supplied URLs validates scheme (https only, unless there is a documented exception) and resolves the host **before** connecting.
- [ ] Resolved addresses are checked against a deny-list: loopback, link-local, private ranges, and cloud metadata endpoints are blocked, with re-validation after every DNS resolution (DNS-rebinding defense).
- [ ] Redirects are followed only with re-validation of each hop, or not followed at all.
- [ ] Webhook and fetch-by-URL features apply the same outbound rules as direct user requests.
- [ ] Outbound requests run with credentials stripped — internal service tokens are never attached to requests whose target came from user input.

### Path traversal

- [ ] File paths built from user input are resolved and verified to remain inside the intended base directory (`realpath` + prefix check) — including archive members on extraction (zip-slip defense).
- [ ] Upload filenames are sanitized or replaced entirely (server-generated names); extension allow-lists are enforced, and uploads are stored outside any executable/web-served path.
- [ ] Download/export endpoints serve by internal identifier, never by client-supplied filesystem path.
- [ ] Symlink following is disabled or checked where the process writes into shared directories.

### Output encoding (companion to all of the above)

- [ ] Context-appropriate output encoding for HTML, attribute, JavaScript, URL, and CSS contexts — templating auto-escaping is on and not bypassed with raw/mark-safe constructs on user data.
- [ ] File download responses set a safe `Content-Type` and `Content-Disposition`; user-supplied data is never reflected into response headers unencoded.

## 4. LLM & Agent Security

Defends AI features (chat, copilots, autonomous agents, tool-using assistants) in the audited system.

### Prompt injection (direct)

- [ ] System instructions are separated from user content at the API level (dedicated system role/field), and user text is never concatenated into the system prompt.
- [ ] The model is not relied upon as the sole enforcement point: security decisions (authorization, data access, payments) are made in code, not by model output.
- [ ] Instructions that the model must treat as untrusted data are explicitly framed as such in the prompt design.
- [ ] Outputs that will be parsed (JSON, SQL, commands) come from structured/constrained generation or are schema-validated before use — free-text model output is never executed or interpolated into queries.

### Indirect injection

- [ ] Content fetched by the agent (web pages, documents, emails, tickets, repository files) is treated as untrusted input: it is quoted/delimited in prompts, never followed as instructions.
- [ ] Retrieved content is sanitized or summarized through a defensive pass before it can influence tool calls.
- [ ] Sources are labeled in context so the model (and reviewers of transcripts) can tell tool output from user intent.
- [ ] Agent browsing/fetch features enforce the same SSRF and URL allow-list rules as the rest of the system.

### Tool abuse

- [ ] Every tool exposed to the model declares a minimal scope (read-only vs write, which resources, which actions) and enforces it server-side.
- [ ] Destructive tools (delete, deploy, send, pay) require a confirmation step or policy check outside the model — model output alone can never trigger them.
- [ ] Tool arguments are validated with the same rigor as public API input: the model is one more untrusted client.
- [ ] Tool execution runs with least-privilege credentials, scoped per tool, never the operator's full identity.
- [ ] Loops are bounded: maximum iterations, maximum spend, maximum side effects per run; runaway agents halt safely.

### Insecure output handling

- [ ] Model output rendered in a browser is HTML-encoded like any other untrusted string (stored prompt injection → XSS is the same defect class).
- [ ] Model output used in code generation or config is reviewed/linted before execution; nothing is `eval`-ed.
- [ ] Generated SQL/commands are executed through the same parameterized/argument-array paths as above.
- [ ] Model transcripts and tool logs are stored with the same sensitivity rules as user data, and secrets reaching a transcript are redacted.

## 5. Secret Management & Sensitive Data Exposure

- [ ] No credentials, API keys, tokens, or connection strings in source, fixtures, seeds, tests, docs, or comments — scanners (Skylos and the platform secret scanner) run as the gate, and any finding is rotated, not just deleted (deletion does not un-leak git history).
- [ ] Secrets are provided at runtime via a secret manager or environment injection; `.env` files are gitignored, and only `.env.example` with placeholder values is committed.
- [ ] Secret values are never logged: log statements, error messages, and exception reports are audited for credential/PII leakage; verbose/debug logging cannot be enabled with secrets in scope in production.
- [ ] Different environments use different credentials; production secrets are not reachable from staging/dev code paths.
- [ ] PII is inventoried and minimized: fields collected have a purpose, storage is encrypted at rest where required, and retention/expiry is configured.
- [ ] Sensitive data in transit uses TLS everywhere, including internal service-to-service traffic.
- [ ] Client-visible payloads (API responses, error pages, source maps in production, bundled JS) do not contain internal identifiers, secrets, or debug data.
- [ ] Backups and exports containing sensitive data are encrypted and access-controlled like the primary store.
- [ ] Secret rotation is documented and tested: rotation does not require code changes or downtime, and old values are revoked after rotation.
- [ ] Dead code, commented-out blocks, and unused config branches that once held credentials are removed — they are the highest-signal residue an attacker greps for (this is a core Skylos target).

## 6. Infrastructure & API Security

### CORS

- [ ] CORS allow-list is explicit per origin — no wildcard origins on authenticated endpoints, no reflecting arbitrary `Origin` headers back with credentials allowed.
- [ ] Credentials-bearing cross-origin responses restrict `Access-Control-Allow-Origin` to enumerated trusted origins only.
- [ ] Preflight handling and allowed methods/headers are minimal — only what the frontend actually uses.

### Rate limiting & abuse controls

- [ ] Rate limits exist on all public endpoints, with tighter limits on auth, password reset, OTP, search, and generation endpoints (LLM endpoints also cap spend/tokens per user).
- [ ] Limits are enforced server-side at a shared layer (gateway, middleware, or edge), not per-instance in-memory where a second instance bypasses them.
- [ ] Request body size, upload size, pagination page size, and list depth are all capped.
- [ ] Long-running/expensive operations are queued with concurrency limits, not executed inline per request.

### Security headers & transport

- [ ] `Content-Security-Policy` set with no `unsafe-inline`/`unsafe-eval` where avoidable; `X-Content-Type-Options: nosniff`; `Referrer-Policy`; `Strict-Transport-Security` on all HTTPS responses.
- [ ] TLS versions and cipher configuration meet current guidance; certificates renew automatically.
- [ ] Framework debug modes, stack traces, and verbose error pages are disabled in production; errors return generic messages with a correlation ID logged server-side.

### API surface

- [ ] API versioning exists and deprecated versions are retired on a schedule — old versions run the current authorization code, not frozen vulnerable copies.
- [ ] Mass-assignment defense: request DTOs allow-list bindable fields; client JSON cannot set internal fields (role, tenant, price, owner).
- [ ] Error responses do not enumerate valid resources differently from invalid ones where that difference leaks account/data existence.
- [ ] Introspection/admin endpoints (API docs, health, metrics, actuator-style routes) are authenticated or network-restricted in production.
- [ ] Dependencies are pinned and scanned for known vulnerabilities on a schedule and in CI; the audit notes the last scan date and result.

---

## Reporting Discipline

1. Record per item: `pass` / `fail` / `n/a` / `could not check` — with evidence (file:line) for every claim.
2. Never read back your own writes as evidence: the fact that a fix was written is not proof the check passes; re-verify after the fix.
3. Failures of `blocking`/`high` items stop the gate; the report goes to Reviewer/Shipping with disposition per finding.
4. Redact any secret values encountered — reference location, never content.
