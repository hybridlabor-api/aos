## Question

Lanternfish is a fictional reporting service. Exports of large reports currently run inside the web request and time out for about 4 percent of customers. Which mechanism should run exports in the background?

**Constraints**

- Ship within one quarter with a team of three.
- No new managed service that needs an on-call rotation.
- Failed exports must be retried and visible to the customer.

## Options

<Compare beforeLabel="Option A: database-backed queue" afterLabel="Option B: managed message broker">
<Before>

Jobs live in a table in the existing Postgres database; workers poll with row locks.

- Zero new infrastructure.
- Throughput tops out around a few hundred jobs per minute.
- Retries and dead jobs are plain SQL.

</Before>
<After>

Jobs are published to a hosted broker; workers subscribe.

- Scales far beyond current need.
- Adds a service, credentials and a monthly bill.
- Retries and dead letters come from the broker.

</After>
</Compare>

## Recommendation

<Decision title="Which queue" question="Which mechanism should run Lanternfish exports?" options={[
  { id: "table", label: "Database-backed queue", detail: "Fits current load with 7x headroom and needs no new service.", recommended: true },
  { id: "broker", label: "Managed message broker", detail: "Better long-term ceiling, but costs a sprint and a vendor today." },
]}>

Start with the table queue behind a small interface (`enqueue`, `claim`, `complete`, `fail`). If sustained load passes 150 jobs per minute, swap the implementation for a broker without touching callers.

</Decision>

<Callout tone="warn" title="Risks">

Polling workers can hold row locks too long if a job hangs; set a claim timeout of 10 minutes. The benchmark ran on a laptop, so repeat it on staging before relying on the headroom figure.

</Callout>
