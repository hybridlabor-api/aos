## Goal and constraints

Parcelly is a fictional service that tracks parcels for small online shops. Carriers push scan events, shops and customers read the current status.

- Show the latest status within 10 seconds of a carrier scan.
- Handle 300 events per second at peak, 20 million parcels stored.
- Keep a full event history for 12 months.

<Table title="Constraints" columns={["Constraint", "Value"]} rows={[
  ["Team", "Three engineers, no dedicated ops"],
  ["Budget", "Managed services only, under 1,500 per month"],
  ["Availability", "99.9 percent for reads, writes may queue"],
  ["Compliance", "Customer addresses deleted 90 days after delivery"],
]} />

## Decision

<Decision title="How do events reach the database?" question="Which delivery path do we use between the gateway and the parcel database?" options={[
  { id: "queue", label: "Managed queue and worker", detail: "Absorbs carrier bursts, retries on failure, one more moving part.", recommended: true },
  { id: "direct", label: "Gateway writes to the database directly", detail: "Fewest parts, but bursts hit the database and carrier retries duplicate rows." },
  { id: "stream", label: "Event streaming platform", detail: "Strong replay, too heavy for three engineers." },
]}>

Carriers retry aggressively when we answer slowly. A queue lets the gateway answer in milliseconds and the worker deduplicate by carrier reference and event time.

</Decision>
