# Fix: duplicate invoice emails

## Symptom

Ledgerly is a fictional invoicing service. Since release 2.14 some customers receive the same invoice email two or three times. Support counted 38 reports in nine days, all for invoices sent from the scheduled run at 06:00 UTC.

- Affected: scheduled invoices only, manual sends are fine.
- Impact: customer confusion, no double charge.
- Severity: medium, no data loss.

Reproduces locally in about one run in three with two workers and an artificial 50 ms delay in the mail client.

## Root cause

The scheduler selects due invoices and sends them in two separate steps. Two workers can select the same row before either marks it as sent.

<Mermaid label="Race between two workers" source={"sequenceDiagram\n  participant W1 as Worker 1\n  participant DB as Database\n  participant W2 as Worker 2\n  W1->>DB: SELECT due invoices\n  W2->>DB: SELECT due invoices\n  DB-->>W1: invoice 4012\n  DB-->>W2: invoice 4012\n  W1->>W1: send email\n  W2->>W2: send email\n  W1->>DB: UPDATE sent_at\n  W2->>DB: UPDATE sent_at"} />

<Callout tone="warning" title="Why it appeared in 2.14">

Release 2.14 raised the worker count from one to three. With one worker the race could not happen, so the missing claim step went unnoticed for two years.

</Callout>

## Fix plan {#fix}

Claim the row atomically before sending. The claim is a single UPDATE that only succeeds for one worker.

<Decision title="How do we claim an invoice?" question="Which mechanism prevents two workers from sending the same invoice?" options={[
  { id: "claim", label: "Atomic claim with UPDATE ... WHERE status = 'scheduled'", detail: "One statement, no new infrastructure, safe across workers.", recommended: true },
  { id: "lock", label: "Advisory lock per invoice", detail: "Works, but the lock must be released on every error path." },
  { id: "single", label: "Back to one worker", detail: "Hides the bug and loses the throughput gain." },
]}>

The atomic claim fixes the cause in the one place every send path goes through, and a crashed worker is recovered by a timeout on the claim.

</Decision>

<Diff filename="server/scheduler/send-due.ts" language="typescript" summary="Claim before send" before={"const due = await db.invoices.findDue(now);\nfor (const inv of due) {\n  await mailer.send(inv);\n  await db.invoices.markSent(inv.id, now);\n}"} after={"const due = await db.invoices.findDue(now);\nfor (const inv of due) {\n  const claimed = await db.invoices.claim(inv.id, workerId, now);\n  if (!claimed) continue;\n  await mailer.send(inv);\n  await db.invoices.markSent(inv.id, now);\n}"} />
